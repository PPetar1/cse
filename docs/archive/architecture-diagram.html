One game, two frontends, four layers. Dependencies only point downward — the interface layer talks to Game's public API, the foundation never calls back up. This is a still image of that shape, not a live document — see docs/archive/README.md.

01 Interface layer talks to Game, owns no rules of its own
main.rs

Wiring only — builds the SharedGame, spawns the terminal thread, runs the GUI on the main thread.

terminal/

Rustyline REPL; command.rs holds the Command enum + parser.

gui/

egui/eframe window — menu, map_view, inspector, file_picker.

ai.rs

Rule-based opponent, per-faction take_turn — no pathfinding or combat logic of its own.

⇄ terminal & gui share one Arc<Mutex<Option<Game>>> — each sees the other's commands immediately

04 Foundation data model + pure algorithms — no game:: or file I/O

Field notes — load-bearing, not obvious from the file tree
▸Sealed state

Game.state is private. Everything outside game/ reads through Game's own query methods — never game.state.* directly. A new frontend need is a new query, not wider field visibility.

▸One game, one mutex

Terminal and GUI run against a single Game behind an Arc<Mutex<Option<Game>>>. There is no syncing step — each side's next read simply sees the other's last write.

▸Turn flow is a flat index

player_on_turn is one index into faction-grouped players. Most turn handoffs are a plain pass to the next player; begin_turn/doctrine settlement fire once per faction per turn, at its first/last player only.

▸Config / runtime split

TOML-facing config types split from runtime types wherever postcard's untagged-enum limit or a scenario-dependent default forces it — not a blanket rule, only where one of those two reasons applies.
